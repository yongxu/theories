This page is the shared channel that does not depend on messages: every session reads it and claims an item before writing new Lean or a new result. It records who is doing what, not scientific status (that lives in the result records), and it changes no authorization (that lives in [GOALS](../GOALS.md) and the [directive register](RESEARCH-DIRECTIVES.md)).

Target: Ren's "unified, complete, enclosed, 0 axiom full theory", following the [four parts of completeness](RESEARCH-DIRECTIVES.md) and the [zero-premise redirect](../sources/15-codex-theory-conversations/2026-10-11-zero-premise-laws.md), checked by the completion criterion K1–K7: coverage, unity, premises, representation, enclosure, the ethics chain and the open register, each with the check that runs it ([study §218](research/2026-10-05-generative-foundation-review/root-foundation/BECOMING-RENEWAL-READING.md#218-r25-the-twentieth-reviews-step-1-docs-now); adopted 20 October 2026 with Ren's approval, [source](../sources/15-codex-theory-conversations/2026-10-20-fix-all-twentieth-review.md)). ## Rules

1. **Claim before proving.** Before any new Lean (core or periphery) or new result, read this page, add a row or edit your own row with the owning session, scope and workspace path, and only then start.
2. **Do not reprove an item another session holds.** If you hold verified work that overlaps it, give the path to the owner, who decides whether to merge, cite or drop it.
3. **One integrator.** The integrator of the zero-premise line decides order, interfaces (the shared definitions) and merges; a new module builds on its definitions rather than setting up parallel ones. While no integrator is named, landers take the queue in order of readiness, and a change to a shared definition is decided on this page by the owner of the module that defines it ([Ren, 18 October 2026](../sources/15-codex-theory-conversations/2026-10-18-constraints-fix-all.md)).
4. **Edit only your own rows; reread before writing.** Update your row when ownership changes, or when the item lands or is dropped. Landed rows move to the history file in the landing commit; the open-claims table holds only open items. A claim whose owner has been inactive for three days lapses: any session may move it to the history file, marked lapsed, and it can be reclaimed. The integrator may append the landing commit to an owner's closed row and move it (clause added after review item B7, Ren: yes).
5. **Landing queue.** One checker run at a time, in the queue's order. The checkers reuse Lean steps that passed on identical inputs, so a run compiles only the changed modules and those depending on them; `BECOMING_FRESH=1` runs everything ([Ren, 11 October 2026](../sources/15-codex-theory-conversations/2026-10-11-unified-head-and-incremental-checks.md)). Build scratch modules with [`scratch_build.py`](../experiments/integrated-correction/general-framework/generative-basis/lean/becoming/scratch_build.py), which stores passed steps in the same cache for the landing run to reuse ([Ren, 12 October 2026](../sources/15-codex-theory-conversations/2026-10-12-checking-efficiency.md)).
6. **This page governs where messages fail.** Messages can be held or expire; a row here is the claim.
7. **One head.** Before starting new Lean, land verified work on main through the queue, or hand it to the integrator. Set superseded drafts aside, and leave scratch that holds unlanded work with its owner ([Ren, 11 October 2026](../sources/15-codex-theory-conversations/2026-10-11-unified-head-and-incremental-checks.md)).
8. **Structural names on joining.** When a module outside the spine is joined or reworked, the core law, the periphery instance (correspondence) module and the record's title state its structure in the core's existing vocabulary. A dualist or limited-scope name (such as IdealWarrant's Warrant, Admits, Permitted) is not carried over, and a correspondence module is named after the core law it instantiates. The original file keeps its path, namespace and bytes ([Ren, 16 October 2026](../sources/15-codex-theory-conversations/2026-10-16-joined-module-names.md)).
9. **Generalize below, not beside.** A module that generalizes an existing law lands below it and proves it, or proves it as a corollary; it does not land beside it with a second proof and a theorem saying the old law is its case. Where the general module is pure and low, the special module imports it and derives its law from it, and the direct proof goes. A new module is imported by an existing one, or its row says why it is a leaf (an instance, a tool, a model). Reason: a theory is unified when the general law is the reason for the special one; landing beside it adds a second reason, raises the counts and leaves two paths to one fact ([twentieth review, theme 2](research/2026-10-05-generative-foundation-review/root-foundation/BECOMING-TWENTIETH-REVIEW.md#2-generalizations-beside--概括落在旁边); added 20 October 2026, Ren: yes). Items claimed before the rule keep their scope; their owners decide whether to apply it.
