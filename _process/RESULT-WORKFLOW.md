# Contributing through canonical results

AI-authored implementation of [Ren's request of 8 October 2026](../sources/15-codex-theory-conversations/2026-10-08-result-centered-repository.md), rewritten in English on 17 October 2026 for the restructure ([previous text](history/2026-10-17-instructions/RESULT-WORKFLOW.md)). It governs research coordination, not research goals or proof standards. Where files go is in [REPOSITORY-LAYOUT.md](REPOSITORY-LAYOUT.md).

## Where the current claim lives

Each migrated claim has one editable JSON record in [results/records](../theories/becoming/results/records). The [register](../RESULTS.md) and the record pages are generated reading views. A record states the claim, assumptions, interpretation, evidence, status, dependencies, boundaries, aliases and next substantive delta. Proofs stay in their modules and arguments in their chapters and studies; records point to them rather than copying them. A record registers a scoped claim, not a whole session or a broad theme.

Authority is scoped. A record controls the maintained summary and reuse identity of its migrated claim; it does not overrule contradictory source evidence, Ren's instructions or independently authorized goals. Source drift suspends a claim of current documentary agreement until the change is read and reconciled. Unmigrated claims keep their canonical chapters, studies and validation scope. The register is a bounded migration, not a semantic deduplication of every historical proof, and searching it is not an exhaustive literature or repository audit.

## Before starting or continuing a study

1. Read the entry points and the governing method ([AGENTS.md](../AGENTS.md)). Search the register by claim, supplied premises and theorem aliases, and inspect the linked sources. Search studies and Lean declarations too, because migration is incomplete.
2. In the existing study note, name the result IDs reused and the exact new contribution: stronger conclusion, weaker premise, new correspondence, application, counterexample, correction, or a previously missing composition. For an unmigrated claim, identify its source and migrate it when the study substantively changes it. Do not create a new study copy to get a fresh workspace.
3. State the output-to-input connection addressed and what would change the account. A new source survey, recheck, proof wrapper, notation change or repeated acceptance is evidence for the same result unless it changes substantive content. Completed mechanisms are reused; a historical "next step" is not automatically today's task.

Use this short block inside the existing study, not a new report every turn:

```text
Result(s): existing IDs, or the canonical source awaiting migration
Delta: what this contribution adds or changes
Supplied premises / correspondence: what remains assumed
Evidence: exact proof declarations + source-bound receipt, argument review, or empirical record
Boundary: retained counterexample or the scope that is still unmet
Integration: which existing record changed; which output now meets which input
```

## One identity, explicit relationships

| Contribution | Record action |
|---|---|
| Alias, wrapper, recheck, repeated acceptance | Add alias, evidence or history to the same record; do not count another result. |
| Same claim with better evidence or corrected exposition | Update the same record; preserve the earlier source or receipt and explain the correction in history. |
| Stronger theorem or weaker hypotheses | Give the substantively different claim its own ID; keep and link the narrower result. Supersede only when the earlier claim or status is actually replaced. |
| Application | Link the reused result with `application`; name the real correspondence and added premises. |
| Formal composition | Use `formal-reuse` only for a verified inference using the cited result, naming producer output, consumer input, preserved hypotheses and the connecting declaration or receipt. |
| Conceptual connection | Use `interpretive` for an argument dependency, or `related` for analogy. Neither is a checked adapter. |
| Counterexample or failed candidate | Preserve the case and its target scope. Revise or withdraw the affected claim without erasing its history. |

Identical wording can cite different namespaces, definitions and test scopes, so it does not establish a duplicate. Several local results holding separately are not a composed proof in one history. Normative warrant, recognition, motivation, implementation and continued preservation each keep their own inferential burden.

## Update and verify

Edit the affected `records/<id>.json` in a directory listed in `_process/research-config.json`. Shared tools live in `tools/research/`; old dated commands stay as compatibility entry points. Two schemas validate side by side: schema 1 (the seeded records) and schema 2, used for every new and migrated record ([Writing a record](#writing-a-record-schema-2)). Text fields are `{"en": …, "zh": …}` objects carrying English, Chinese or both; full translation is not required, and generated pages show the English, or the Chinese where English is missing. IDs are stable semantic names, not dates or session IDs. `canonical_source` and every boundary must refer to a listed source. Record formal names as aliases where they denote the same result; do not use a whole module as an alias for one lemma.

**Statuses.** `recorded-checked` needs a proof source and a successful existing receipt with an exact source-hash field. `reviewed-scoped` needs a substantive statement and review. `open` is an unmet target, not a failed local theorem.

**Hashes.** Source hashes record what was read; never refresh them to silence a check. When a source changes, read its diff and the relevant context, revise the claim or scope if needed, then update that record's hashes. A change to the claim, the premises, the scope or a declaration list takes a history note in the record. A re-point that changes nothing the record says (a reviewed hash, a proof binding's receipt) takes none: it is made with `tools/research/repoint.py`, which writes one line per landing to `_process/architecture/rebinds.jsonl` (since R35, 20 October 2026; the earlier notes of this kind are condensed, see [Record history](#record-history)). Preserve old scientific receipts rather than editing them to match new bytes. A changed mathematical claim needs an actual Lean check; documentary reorganization alone does not. `reviewed_at_utc` is the documentary review time: refresh it whenever the record's content changes (claim, premises, correspondence, limitations, counterexamples, related notes or next step), not when only a validation scope is re-pointed to a newer receipt.

```sh
make research-find QUERY=support
make research-render
make research-check
make research-links
python3 -B tools/research/research.py check --ids joint-plan-composition
python3 -B tools/research/research.py check --changed-since HEAD
python3 -B tools/research/research.py lint --ids joint-plan-composition
```

**Markdown drift.** A Markdown source drifts for a record only where the record's reviewed text changed. The checker finds the reviewed version in `HEAD`'s history by its hash and compares it line by line (a paragraph, list item or table row is one line). Added lines change nothing the record was reviewed against. A rewritten or removed line counts if it links the record's page, lies in a `##` section the record cites by anchor (`path#anchor` anywhere in the record), or comes before the first `##` heading. If the source neither links the record nor is cited by anchor, every rewritten line counts. A reviewed version missing from history counts as drift. While a merge is in progress, `HEAD` does not yet hold the incoming commits, so a record reviewed on the incoming side shows false drift of its whole source; render and check after the merge commit. Lean sources, receipts and all other files need their exact bytes. The record keeps its reviewed hash, and `check` reports sources changed only outside what was cited (`changed_outside_cited`). When a landing appends a study section or edits other records' rows in the chapter, untouched records need no rebinding and no history note. A record that wants this precision for a long source cites its sections by anchor. The comparison depends only on the two texts, so the checker keeps each one outside the repository, one small file per pair of texts named by their sha256 under a tag of the algorithm and Python's version, in `~/.cache/research-drift-comparisons/` (or `$RESEARCH_DRIFT_CACHE`); an entry that cannot be read or does not fit is computed again, and deleting the directory costs only time.

**Exit codes and scope of the checker.** A stale record keeps its earlier page; healthy records and shared indexes still render. Exit 1 means invalid metadata, an unincorporated concurrent edit or outdated rendering; exit 2 means source drift in the selected records, with other records' drift reported separately. Changed-file selection follows result dependencies as well as direct references; dependency metadata is always checked globally. No hash is refreshed automatically. The checker verifies structure, references, declaration presence, receipt hash bindings, unique aliases, dependency cycles and generated views. It does not prove semantic equivalence, audit every transitive import or establish the warrant of premises; hypotheses hidden in definitions remain a review obligation.

<a id="record-history"></a>

**Record history.** `history` keeps the notes that say what changed in the record: its creation, a changed statement, title, premise, law or scope, a correction, a supersession, an adopted reading or vocabulary. A re-point or rebinding that changes nothing the record says is not a history note: `tools/research/repoint.py` makes it and logs it once per landing in `_process/architecture/rebinds.jsonl`. The bookkeeping notes written before 20 October 2026 were condensed by `research.py compact-history` (R35): each record keeps one note counting them with their date range, and its exact bytes before compaction are stored under `_process/architecture/history/` (named in that note, and listed in `text_versions` for schema-2 records), so nothing is lost. The classifier is `tools/research/history_notes.py`; the receipt `_process/architecture/compactions/2026-10-20.json` gives each record's counts and hashes.

**Law families.** Records that state one law and its readings, conditions or calibrations are grouped in `theories/becoming/results/data/law-families.json`, each family with a lead record and one shared statement. A new record that restates a family's law joins the family there instead of repeating the statement; the record pages and RESULTS.md render the family, and `research.py check` verifies that every member is a record and sits in one family. The record field `family` is the session-map family and is not this.

**Renaming a record.** `research.py rename-id --plan PLAN.tsv` (old_id, new_id, reason; dry run unless `--apply`) moves the record to the new id, keeps the old one in `former_ids`, rewrites links, JSON references and the id's mentions in current-facing text (study logs, reviews and the board keep the id of their time), and writes a receipt to `_process/architecture/renames/`. The old record page becomes a generated redirect, and `research-find` matches former ids. A passage map built by a script (the RO map) follows through its builder, never in place. An id named in the curated chain's data is renamed only through the chain's maintenance record.

**Supersession.** Keep the old record with `status: superseded` and `superseded_by: <id>`, record the exact replacement scope and preserve the old evidence. `withdrawn` needs an explanation in history and a linked boundary; it never deletes the counterexample.

### Moving a source

A record's sources move only with `python3 -B tools/research/research.py move --plan <paths> …`, read the plan, then the move itself (see [REPOSITORY-LAYOUT](REPOSITORY-LAYOUT.md#history-layout)). The move writes the manifest and receipt, re-keys `canonical_source` and references by exact path substitution with the hash carried over, and `reviewed_version` follows the move receipt. Any other byte change to the source is read and rebound as above. Run `make research-links` afterwards.

### Lead the README with significant completed results

Maintain the ordered `readme_featured_results` list in `_process/research-config.json`. Each selected record has status `recorded-checked` or `reviewed-scoped` and an `overview` with `title`, `summary` and `evidence` text fields; the English leads the README and the record page shows what the record carries. Keep the summary faithful to the claim's explicit premises and validation scope, and distinguish checked inference from philosophical argument. Selection and renaming create no result and strengthen no proof. Render and check; never edit the generated README.

The optional ordered `readme_research_goals` list selects scoped goals for the README's ongoing-research section, each with an `overview` (`title`, `summary`, `next_step`), keeping its authorization, premises and completion criteria. Established-result links come from the goal's `result_ids`, limited to `recorded-checked` and `reviewed-scoped` results. Do not add a parallel scientific-status field to goals or present open targets as achievements; this navigation validates nothing.

README's first screen is the file `readme_first_screen` names, placed before the opening, its reading times and counts filled at render (`navigation.first_screen`). It times the files its `{{time:PATH}}` fields name (the one page), so an edit to one of them needs `make research-render`, or the check finds README stale.

## Writing a record (schema 2)

Say what the result does, then its exact conditions. Write only the boundaries the theorem or argument actually carries. Round numbers, sections, receipt times, sessions and "nothing new this round" belong in history and evidence, not public fields. Schema 2 (`"schema_version": 2`) applies to every new record and every record migrated from schema 1; schema-1 records validate unchanged until migrated. Limits below are per language present (English / Chinese characters).

| Field | What goes in it | Limit (en / zh) |
|---|---|---|
| `title` | A short name, not the statement. | 100 / 40 **(error)** |
| `statement` | What the result does, or what the target asks, in one or two positive sentences. No Lean names, round numbers, sections, dates or receipts. Rendered first, under the title. | 300 / 150 **(error)** |
| `claim` | Optional: the exact statement with its conditions written in, when `statement` is not already exact. | 1500 / 700 |
| `laws` | Optional: one law per item with `declarations`, each named in `references`. A family of laws goes here, not into `claim`. An item's keys lie among `en`, `zh`, `declarations` and `statements_at_model` (F5, below). | 420 / 190 each |
| `boundary` | Only on U4's boundary record: the standings of central declarations on the edge and the two premises of the ethics (the boundary field, below). | — |
| `hypotheses` | Premises the result uses: logical commitments, supplied laws, normative commitments, correspondence assumptions. | 420 / 190 each, 9 items |
| `does_not_show` | Replaces `limitations`. Substantive non-implications only, one sentence each, typed by `kind`: `non-implication`, `converse`, `correspondence` or `scope`. An optional `witness` names a declaration in `references` or an alias. | 240 / 110 each, 8 items |
| `counterexamples` | Witnessed cases with their hashed source, as in schema 1. A record needs counterexamples or `does_not_show`. | — |
| `standard_boundaries` | Keys of boundaries shared by many records, defined once in the file named by `standard_boundaries` in the config. Cite a key instead of writing its sentence out. | — |
| `not_required` | Targets: what the target does not ask. | 200 / 90 each, 6 items |
| `progress` | Targets, assessments, arguments: one line per completed connection, with its boundary; `source` is a hashed reference, optionally with an anchor (`path#anchor`) that must exist. | 240 / 110 each, 16 items |
| `validation_scope` | The current evidence in one paragraph: the kind of evidence and where its receipts are. | 600 / 260 **(error)** |
| `next_delta` | The next substantive step, stated positively. | 400 / 180 **(error)** |
| `correspondence` | As in schema 1; rendered inside the folded block. | 1200 / 500 |
| `history` | Everything about rounds: who asked and when, which round or section, which receipt, what was reused or not recounted. | — |
| `text_versions` | Hash-bound snapshots of the record's earlier bytes: `path`, `sha256` and a `note`. | — |

Other fields (`id`, `kind`, `status`, `family`, `reviewed_at_utc`, `canonical_source`, `aliases`, `dependencies`, `related`, `references`, `proof_bindings`, `overview`) keep their schema-1 meaning and checks. The [migration drafts](research/2026-10-05-generative-foundation-review/history/root-foundation/development/becoming-general-laws-plan/readability/drafts) show three complete schema-2 records with sentence-by-sentence mapping tables (examples, not installed records).

**Never in the public fields** (`title`, `statement`, `claim`, `laws`, `does_not_show`, `not_required`, `progress`, `counterexamples`, `next_delta`, `overview`):

- round numbers (P92), section numbers (§29), dates, receipt timestamps (20261013T125626Z), session ids ([1c3084]) or round narration ("this round", "has landed", 本轮, 已落地);
- the status in other words ("remains open", "is unproved"): the `status` field says it;
- "no new theorem / Lean run / experiment / independent review": that is `validation_scope`;
- another record's status or scope: link it as a dependency or related result;
- instructions to later sessions ("do not reopen"): those go on the [work board](BECOMING-WORKBOARD.md).

**Replace, do not append.** When a round adds a boundary, reread the existing items: fold the new sentence into the item it refines, or replace the item it supersedes, and record the change in `history`. Each round leaves one history note; receipts stay in `references`, and `validation_scope` names where they are, without a paragraph per round. For a target, a completed connection becomes one `progress` line with an anchored link to the study section holding its argument. The snapshot and git keep every earlier wording.

**Shared boundaries.** The [shared boundary file](../theories/becoming/results/data/standard-boundaries.json) holds each sentence once, with its source. Cite a key only where the sentence is true of the record: `no-ethical-premise` ("No ethical premise and no Lean axiom is used.") only where the hypotheses contain no ethical premise and the bound receipts report empty axioms for the cited declarations. Changing a text there changes every citing page, so it needs the same review as a record; add a key when a boundary recurs across records.

**A short title for a schema-1 record.** Schema 1 also accepts an optional `statement`, rendered under the title and checked as strictly as in schema 2, so a long title can become a short name, with its old text kept as the statement, before full migration.

**Migrating a schema-1 record.**

1. Claim the record on the [work board](BECOMING-WORKBOARD.md); reread its current bytes and `git diff`.
2. Run `python3 -B tools/research/research.py snapshot <id>`. It stores the exact bytes at `_process/architecture/history/<sha256[:16]>/<id>.json` (the `record_snapshots` directory in the config), refuses to overwrite a differing copy, and prints the `text_versions` entry; add it to the record.
3. Set `"schema_version": 2`, write the short title and statement, and map every old sentence to a field, a shared key, `history` or the snapshot. Keep the mapping table in the study that owns the record; nothing is dropped silently.
4. Add one history note and refresh `reviewed_at_utc`. A documentary migration needs no Lean run and refreshes no source hash.
5. Run `make research-render`, then `research.py check --ids <id>` and `lint --ids <id>`. If the [generativity chain](../theories/becoming/results/GENERATIVITY-CHAIN.md) fingerprints the record, reconcile it through its own workflow, once per batch.

**The atlas (AA).** `theories/becoming/results/atlas/` lists the account's dynamics (attractors, locks, drains, absorptions, cycles, closures and kept regions) as a curated layer beside the records: `vocabulary.json`, its closed lists, and `entries/`, written by hand; [`ATLAS.md`](../theories/becoming/results/atlas/ATLAS.md) and `theories/becoming/results/data/atlas.json`, generated by `tools/research/atlas.py` through `make research-render`. It creates no result and strengthens no proof. An entry holds no standing of its own: it shows each of its records' status and kind as the record says, never merged, and an entry with no record says whether it is argued, conjectured, a reading or open, and cites where. Hypotheses are named by their place in a record and quoted from it, so they cannot be paraphrased away. `research.py check` fails on a broken entry: a record, declaration, anchor or test path that does not resolve, a superseded record shown as live, or a dynamic marked good or bad. A change to a record that an entry names does not edit the entry; what the entry's own words say of the record is the writer's to keep true. A new result that states a dynamic adds or extends its entry in the same landing. [The design](research/2026-10-05-generative-foundation-review/root-foundation/development/aa-attractor-atlas/PLAN.md#3-the-atlas-design).

**Shared laws under each law (MV).** A record page shows under each law which of the five shared laws (closure, balance, finite runs, lumping, widening) have an anchor among the constants its declarations use, taken together (a shared law is listed where any of them reaches its anchor). It also shows whether any of them reaches the grammar, the measure's four-way dependence for them together and, for a central declaration of `COVERAGE.json`, the measure's category and reason. This is computed from the Lean dependencies of the declarations by `tools/research/shared_laws.py`, which reads OU3b's measure (`measure_grammar.py`) and the checker's cache, and writes `theories/becoming/results/data/shared-laws.json`. Nothing about shared laws is written into a record. After a landing that changes the Lean, a record's laws, `COVERAGE.json`, the measure, the dump (`THEOREM-CONNECTIVITY.py` and its `.lean`) or the generator, and once `check_becoming.py` has passed on those sources, run the generator and then `make research-render`. A law whose declarations no longer match the data shows nothing. `check` reports, never as an error, how many laws the data no longer matches, whether the core sources it was computed on are still the latest passing receipt's, and whether the measure, `COVERAGE.json`, the dump or the generator changed (`shared_laws`). A file computed from a saved dump (`--dump`) never reads as current. It is a measurement of Lean dependency only. A shared law counts where one of its anchors (the measure's `ANCHORS`: EC's `measure.py` `LAWS` and the law's statement on the grammar) occurs, directly or through other constants, in what the declarations state, define or use in a proof. That does not make it the reason they hold. Reaching none does not make the law no case of a shared law: `Continuity.Balancing` states a balance of its own and reaches none. A shared law's statement on the grammar (08 §7) is among its anchors. The grammar is the measure's: a declaration with a «» name, its vocabulary included (the page marks a reach through vocabulary only). The number and list lemmas of `GrammarLaws` do not count.

**Statements at a model (F5).** A law that states a row of its own record at a model carries `statements_at_model`: items `{"declaration", "of", "models", "review"}`. The declaration is the theorem at the model, among the law's declarations. Its row is among another law's declarations in the same record. The models are among `occurrence` (a World's occurrence model), `process` (a process's model) and `own` (the row's own carrier). The review is a `review` reference of the record that checked the item as it stands, and it names the theorem in code. These declare a correspondence, which a reader judges and Lean does not show; nothing about shared laws is declared. The check enforces the shape. A law carrying items holds no row of an item, and a theorem is the declaration of one item at most. Superseded and withdrawn records carry none. `shared_laws.py` verifies the rest from the checker's cache:
- both names are in the spine run;
- the theorem's walk reaches the row without entering another item's theorem, except one on the same law stating the same row;
- its statement names a grammar term other than «际», also through the definitions of its own module;
- for `occurrence` and `process`, it names a relation of that model;
- its law holds no central declaration.

It lists the grammar terms and what the statement keeps in other terms. A law carrying items is measured like any other, but counted in `counts_at_model`, not `counts`, so a statement at a model raises none of the existing counts (a law that gains items leaves them). An item the check would refuse is written unverified, never counted, except one whose review does not name it: only the check reads the review. `central_reach` separates the distinct central declarations that reach the grammar from those stated at a represented model, those stated only on their own carrier, and the rest. Pages show an item under its law, and under every law naming its row, only while the data verified it and the carrying record still declares it so. Each line marks the item as declared and links its review. An item only on its row's own carrier is labelled so, not as at a model. A law whose items differ from the data's counts among the laws the data no longer matches. `check` lists unverified items in `shared_laws`. A landing that adds items needs none unverified. The design and its reviews are in [architecture/mv/F5-MODEL-STATEMENTS.md](research/2026-10-05-repository-reconciliation/architecture/mv/F5-MODEL-STATEMENTS.md).

**The boundary field (MV).** One record, U4's boundary record, carries `boundary`: `standings`, one entry per central declaration it places on the edge or by a reading, and `premises_of_the_ethics`, the continuation condition (role `scope`) and C (role `order`), each with its definition and the theorem showing it not entailed by the dynamics, or `null` and why. An entry's `standing` is `derived` (with `law`, the grammar laws the row is a case of, and optional `bridges` and `support`), `under a stated hypothesis` (with a root `form`, `hypotheses` of `{hypothesis, countermodel, fit}`, a `recovery` and a `certificate`) or a reading (a distance, or `counting`), each with a `basis` and a `review`. Like F5's `of`, these names declare a correspondence: that the row is a case of these laws through these lemmas, or an instance of this form. They record nothing about which shared laws a row rests on, which stays computed. The rules are in `tools/research/boundary.py`, which the check applies with the review's text (it names every name in code, in full or less its root) and `shared_laws.py` without it. `shared_laws.py` checks the rest: a derived entry's closed set against the checker's cache (D1 to D5), its laws and bridges in Lean, and a form under a stated hypothesis by `tools/research/boundary_check.lean`, run in the core run's environment restored from the cache. Every central declaration the record does not place takes U4's rule, whose fallback is `unplaced`. An entry that fails is unverified and its row takes the rule's label. The record's own laws are counted in `counts_at_boundary_record`, so the field raises no other count. Pages show a central declaration's standing under every law naming it, only while its entry, or its absence, and what the rules read of the record around the field are what the data read; the boundary record's page lists them all with their counts. `check` lists in `shared_laws` the unverified entries and premises, the unplaced rows and the declarations not matched; U4's landing needs all four empty. The design and its reviews are in [architecture/mv/BOUNDARY-FIELD.md](research/2026-10-05-repository-reconciliation/architecture/mv/BOUNDARY-FIELD.md).

**Checks.** `research.py check` runs the readability lint. For schema 2, the caps marked *error*, process markers in public fields and three or more rounds or sections cited in one field are errors. These warn: the other caps; a written-out shared boundary; a restated status; an evidence disclaimer in a public field; a negative opening of the statement; items longer than two sentences; and a word of exchange in a public field (cost, charge, budget, paid, price, spent, credit, fund and the like, or 付费、成本、代价; scientific terms such as Price's equation excepted). Name what the relation does; a record whose subject is an exchange keeps its words. `check_becoming.py` lists spine declaration names with such a word in its receipt (`market_names`). On a schema-1 record every finding warns, except on its optional `statement`; README `overview` fields always warn. Warnings never change the exit status: `check` counts them under `style_warnings` and `lint` lists them. `check --changed-since <commit>` also runs the growth ratchet: a changed schema-1 record whose `limitations`, `validation_scope` or `correspondence` grew in either language since that commit by more than 40 English or 20 Chinese characters fails, and smaller growth warns; migrate to schema 2 before adding text there. A new schema-1 record warns. The lint judges form only; whether a boundary is substantive is the author's reading.

## Integration and concurrent sessions

At study closure, update the affected record and the substantive chapter or study. Do not append status to generated pages (README, RESULTS, RESEARCH, ROADMAP, CLAIMS, GOALS, OPEN-QUESTIONS, DEPENDENCIES, study indexes); `make research-render` derives them from records and scoped authorizations. Earlier text is preserved in linked historical reading editions, with their original anchors. New research authorization goes in the appropriate `_process/goals/<id>.json`, with Ren; scientific status belongs only to result records. Update the generativity chain only when its scientific content changes, through its own hash workflow. The full catalogue stays a reading guide and does not become a second claim register; the session map of 8 October 2026 and the reading volumes and theory map of that date are frozen in [history](../theories/becoming/history/SESSION-RESULTS-2026-10-08.md) (R35).

Sessions may add different record files concurrently. Before editing a shared record, reread its bytes and `git diff`; reconcile new evidence rather than replacing another session's update. Before committing, inspect status and commit only owned paths (`git commit -m … -- <paths>`) unless Ren authorizes a whole-repository checkpoint. After integration, inspect changes since the starting commit, and report incoming work with its paths and scope; do not silently absorb unfinished proofs, refresh their hashes or mark them accepted. Finishing a structural task does not authorize an endless research or monitoring loop.

If a session appended prose to a generated view, reconcile it into the relevant source or record, then run `python3 -B tools/research/research.py preserve-view <path> --note '<review and integration scope>'`. Every prior snapshot stays hash-bound. Rendering serializes cooperating writers, checks metadata and source changes during the run, and refuses unincorporated output changes; it cannot stop an editor changing a file after a check, so rerun after new work arrives. The study indexes count tracked and untracked files, so a lander's new files are listed before its commit; render where the only untracked files are your own, since a render in the shared checkout lists other sessions' drafts and the next clean render reverts it. Before landing, work in a clean worktree you own, switched to the branch (`git switch --detach <branch>` takes seconds; a new worktree takes minutes and 5.3 GB). The order: put the head clause on the Queue line, in a gap; merge main into the branch; run what writes, each through `gate.py hold --` (the core run for changed Lean, the shared-laws generator where the paragraph above asks for it, then the render), and commit it with the landing, docs-only landings included, since committed files are counted and `.lean` files catalogued wherever they lie; write the landed clause in place of the head clause and commit the board with the landing; run `make gate`, and any area check it does not yet run; re-read the Queue line; fast-forward main. `make gate-plan` lists the steps that write and the checks the changed paths reach, with the paths that select each ([GT](research/2026-10-05-repository-reconciliation/architecture/gt/GATE.md)). The gate keeps each pass with the tree it passed on, and when main moves first, re-runs after the next merge only what that move reaches; the steps that write run again where the move reaches them. Run it in the background with a log, and report which checks ran, which were reused and from which tree, and that the full set waits for the phase's end. Its `restated` list names the live lines, outside studies, that link a home section or record statement the landing changed; a reader other than the author re-reads them, and any other page known to restate it. While another item holds the head of the queue, commit nothing to main until it reports landed (board rule 5), claim rows included. A commit between landings (a claim row, a study, a source) renders too where it adds files the views count, scratch `.lean` included, and commits the re-rendered indexes with it. A fast-forward of the shared checkout stops where an untracked file sits at a path the landing adds; compare it with the landing's file, and keep any difference in a commit under `refs/salvage/…` before moving it aside, never deleting it. Keep landing worktrees under `.claude/worktrees/` and commit the kits and logs you need: macOS deletes files under `/private/tmp`, where session scratch directories live, that have not been read for about three days. A board script copied from an earlier kit should match the board's dates in general (the latest-receipt sentence's date, for one, moves past the 29th of a month).

When merging, keep other sessions' changes; the state of the scientific evidence outranks a register label. Integration names the inferences now connected and the correspondences still missing; more indexes or files do not make a theory complete.

## Shared validation and discovery

`make research-check` validates the registry, scoped goals, generated navigation, local targets, original-byte preservation and declared receipt bindings; `make research-links` checks links; `make research-test` tests the tools and runs after any infrastructure change. `make gate` runs, for a landing, those of them its changed paths can reach, and `make gate FULL=1` all of them, once at a phase's end and before a push, reusing only passes kept on the same tree (`FRESH=1` with it reuses none); before a push, `make gate-push` runs the push screen from the remote's main to the tip, and the push stays Ren's. CI runs the check and the tests on every push. It does not build every Lean package or accept a scientific result; mathematical changes go through the source-bound Lean workflow.

`make research-find QUERY=topic` searches canonical claims first, then live theory, studies and working sources, leaving out history, frozen copies and attempts (the path roles in [REPOSITORY-LAYOUT](REPOSITORY-LAYOUT.md#path-roles)). Use `python3 -B tools/research/research.py find topic --archives` for deliberate historical search. `make research-imports` lists textual import candidates, with ambiguous or unresolved names separated; an import does not establish a conceptual composition.

A dependency can carry an `interface` with `output`, `input` and `conditions` text fields and a reviewed `evidence` path. Keep whether the edge is formal reuse, application or interpretation, and reference the exact connecting declaration in the reviewed source; metadata does not establish a new mathematical bridge.
