## Findings

**1. MUST. P4's "shown, not enforced" is enforced by the existing check, and it makes every Lean landing rewrite atlas pages.**
- `tools/research/research.py:471-477`: in a check, any generated page that differs from what a render would write and is not an index page is an error ("generated view differs"). Atlas pages are not index pages.
- `tools/research/gate.py:246-249`: the gate's `strict` check runs `research.py check --strict-fresh` on every path, and `gate.py:290` says it "fails on any page a render would change".
- So once the render hashes module sources and writes "behind" sentences, a Lean landing that does not re-render fails the gate. The design's sentence "The gate does not fail on it" is false in effect.
- It also reverses a stated property of the atlas, `tools/research/atlas.py:25-27`: resolution "is checked, not rendered, so a chapter or Lean edit does not make the pages stale".
- The front-page sentence naming the behind modules would change at every Lean landing, so any two concurrent Lean landings conflict on generated `ATLAS.md`.
- Replacement for P4, first half: "The pages are a function of P1 and the store only. They say what P1 was printed from (the commit and the clock of its header) and never whether the Lean has changed since; a render reads no Lean source for this layer. Being behind is found by a check, not written on a page."

**2. MUST (the rule for item 2). Bind P1 as the core receipt is bound: checked at the landing that changes the Lean, and at no other.**
- For "shown":
  - The layer is no result and should hold back no landing.
  - The reading catalogue already shows drift without failing (`research.py:494-496`).
  - Lean landings already carry a core run and a gate.
- For "enforced":
  - The board's rule for the listing of places is "owed by whoever lands", and `_process/BECOMING-WORKBOARD.md:56` says "nothing under `tools/research` checks the listing against what it reads". It went stale at the first landing by another session (22 November 12:10, same line and line 40).
  - Since 1 November, 136 commits touched the package's Lean (109 non-merge, 213 distinct module files, 10 commits since 15 November). An unrefreshed P1 would be behind for about half the package within a month.
  - Per-module "behind" marks are only approximate. A proof term can change when an imported module changes; `check_becoming.py:4212-4226` keys a module on its whole import closure for that reason. A match of every hash in the tree is exact.
- The precedent that fits is `gate.py:258-259`: the `receipt` check is selected only when the Lean tree changes.
- Replacement for P4, second half: "A gate check `proof-uses`, selected only when a landing changes a Lean file under the package or P1 or the printer, fails unless P1's header binds the bytes of every module in the stub's import closure, the printer and the toolchain. The session landing the Lean runs P2 after its core run, when the cache holds that tree, and before its gate; after a rebase over another Lean landing it runs P2 again. P1 is regenerated, never merged by hand. A landing that changes no Lean never runs P2 and is never stopped by it. This adds one step to every Lean landing; the other sessions' word on it is asked before it is switched on, and until then the check reports and does not fail."
- Strike "Stop another session's landing" from the must-nots, or reword it: "Stop a landing that changes no Lean."
- If the sessions refuse enforcement, keep finding 1's half and have `research.py check` report "printed before N modules changed" in its result. Do not write it on pages.

**8. MUST (P2). Use the checker's slots and a clean tree; do not wait by process name.**
- Dirty sources: `check_becoming.py:4146-4153` indexes the checkout's working files and `scratch_build.py:64` reads their bytes. In a shared checkout P1 can be printed from bytes of no commit, and hashing the files later is a race. P2 should run only where `git status --porcelain` on the Lean tree is empty, record that commit, and take hashes from the bytes it compiled.
- Cold cache: any module whose key is absent is compiled (`check_becoming.py:4432-4460`), with 1,800 s allowed per step (`scratch_build.py:39`). "Half a minute" becomes the whole package; your notes put that at 2,393 s of step time. The tool should print how many steps would run and refuse above a small number unless told.
- Another session building: this part is safe. Same key waits on the key's lock and then reuses; every Lean process takes a machine slot (`check_becoming.py:4385-4423`).
- The printer run: the design starts `lean` on it outside the slots. Wrap it in `cb.lean_slot()`.
- Waiting on a gate: "It waits while a gate, a core run or a scratch build is alive" by process name is the pattern your notes record as deadlocking. Under finding 2 the landing's own gate comes after P2, and a gate takes hours, so drop the wait and rely on slots and key locks.
- Stub tree under `tmp/`: safe from the tools. `/tmp/` is ignored (`.gitignore:23`), outside the module index's root, and `atlas.py:270` reads only tracked files. Each tree restores a copy of every olean (`check_becoming.py:4254`), 323 MB for batch29, and each run stores a new stub entry in a cache already at 41 GB and 163,765 entries. Use one fixed directory the tool owns and overwrites.
- Stub contents: generate it from the file listing, not `import Becoming`, so a module the root does not import is still printed or is named as left out.
- Writing P1: write only after `scratch_build` exits 0 and the printer's last line gives a row count that matches; write to a temporary file and replace.
- Replacement for P2's middle: "It refuses a tree whose Lean differs from a commit; builds a stub generated from the package's module files through `scratch_build.py` in one fixed directory under `tmp/` that it owns; says how many steps the cache lacks and refuses more than a few unless told; runs the printer in one of the checker's Lean slots; and writes P1 only after a clean exit and a matching row count, by replace. It waits on nothing by process name."
