## 2. `closed_or_lost_within`: where each bound is used, and the split at `all.length`

The proof (ll. 140-143):

```lean
⟨(kept_or_lost everyMove everyValue updates inOrOut usableOrNot (all.length + 1) c).imp
   (fun kept => (coded_kept_iff_closed (fun d _ => every d) updates).mp (KeptFor.shorter kept))
   (lostReading_shortens every everyMove),
 fun ⟨closed, lost⟩ => closed_never_lost closed all.length lost⟩
```

- **The kept bound** (`coded_kept_iff_closed`, `.mp`) is used once, in the left branch of the first conjunct (l. 141), after `KeptFor.shorter` brings `all.length + 1` down to `all.length`.
- **The losing bound** (`lostReading_shortens`) is used once, in the right branch of the first conjunct (l. 142), to bring `L (all.length + 1) c` down to `L all.length c`.
- The second conjunct uses neither bound. It uses `closed_never_lost`, that is, `keptFor_of_closed` and `lost_not_kept`.

**The split at `all.length` proves the same statement.** By hand, unchecked:

```lean
⟨(kept_or_lost everyMove everyValue updates inOrOut usableOrNot all.length c).imp
   (coded_kept_iff_closed (fun d _ => every d) updates).mp id,
 fun ⟨closed, lost⟩ => closed_never_lost closed all.length lost⟩
```

The types match: `kept_or_lost … all.length c : KeptFor … all.length (decode c) ∨ L all.length c`, the left branch is exactly the left side of `coded_kept_iff_closed`, and the right is the goal's right disjunct. The implementer's own REPORT says the same: "Starting the split at the length itself would also prove the alternatives using the keeping bound alone."

- **No premise of the theorem falls away.** `every` is still needed as `within` for `coded_kept_iff_closed`. `updates` is still needed there and by `kept_or_lost`. `everyMove`, `everyValue`, `inOrOut` and `usableOrNot` are still needed by `kept_or_lost`.
- **What falls away:** the calls of `KeptFor.shorter` and of `lostReading_shortens`.
- **So `lostReading_shortens` is used nowhere that the final statement needs.** Its one use (l. 142) is on a detour of one step up and one step down. `lostReading_within_length` is used nowhere in the module.

T4 as frozen ("neither half uses the bound"; "the first half must use `coded_kept_iff_closed`") is passed by the letter, since the kept bound is used. But the REPORT's line "the losing branch uses `lostReading_shortens`" is true only of a removable step. The losing side's bound (Part A.2) contributes nothing to `closed_or_lost_within`.

## 3. Does each bound follow from the other with the either-or?

Below, `len := all.length`, `KC := coded_kept_iff_closed (fun d _ => every d) updates`, and `KL := kept_or_lost everyMove everyValue updates inOrOut usableOrNot`. Both derivations are by hand and unchecked.

**(a) The losing bound from the kept bound.** Under the theorem's premises, `∀ n, L n c → L len c` follows from `kept_or_lost`, `coded_kept_iff_closed` and `closed_never_lost`, with no use of `lostReading_*`:

```lean
fun n lost => (KL len c).elim
  (fun kept => False.elim (closed_never_lost (KC.mp kept) n lost)) id
```

It needs the kept bound, since `closed_never_lost` at an arbitrary `n` goes through `keptFor_of_closed`. From `kept_or_lost` and `lost_not_kept` alone it is blocked: they give `KeptFor len ∨ L len`, and `lost_not_kept` excludes `KeptFor n` only at the same `n`. Without a bound, `KeptFor len` does not give `KeptFor n` for `n > len`. With `n ≤ len`, `lost_not_kept` and `KeptFor.shorter` (repeatedly) would suffice, but the bound is for every `n`.

So, under Part C's premises, `lostReading_within_length` is a corollary of the kept side. Standing alone, it holds under fewer premises: only `every` and `everyMove`, with no `updates`, no decisions and no values list. That is what it has over (a).

**(b) The kept bound from the losing bound.** The direction `.mp` of `coded_kept_iff_closed`, `KeptFor len (decode c) → InClosedFamily … (decode c)`, follows from `lostReading_within_length`, `kept_or_lost`, `lost_not_kept` and `updates`. Take the family of classes covered by a code that is never lost:

```lean
-- F B := ∃ d, (∀ n, ¬ L n d) ∧ ∀ s, B s → decode d s
have never (d) (k : KeptFor … len (decode d)) : ∀ n, ¬ L n d :=
  fun n lost => lost_not_kept len d (lostReading_within_length every everyMove n lost) k
fun kept => ⟨F, ⟨c, never c kept, fun _ b => b⟩,
  -- guard: kept_or_lost 0 d is inOrOut d; Outside d is L 0 d, excluded
  fun B ⟨d, nl, sub⟩ s b => ((KL 0 d).resolve_right (nl 0)) s (sub s b),
  -- closed: kept_or_lost (len+1) d, the lost side excluded
  fun B ⟨d, nl, sub⟩ => match (KL (len + 1) d) with
    | .inr lost => absurd lost (nl _)
    | .inl ⟨safe, a, usable, next⟩ => ⟨a, fun s b => usable s (sub s b), fun o =>
        match updates d safe a usable o with
        | ⟨e, names⟩ => ⟨e, never e (KeptFor.mono (fun s => (names s).mpr) (next o)),
            fun t seen => (names t).mpr (Seen.mono sub seen)⟩⟩⟩
```

(`resolve_right` is written for brevity. The constructive form is `.elim id (fun o => absurd o (nl 0))`, since `L 0 d` is `Outside … d` by `iter`'s first equation.) This uses `every` only through the losing bound, not as `within` for `iter_postfixed`. **So each bound follows from the other under Part C's premises.** `closed_or_lost_within` needs exactly one of them, and the module proves both.

Both bounds reduce to the same induction on a list, `Iteration.extend_at_places`. The kept bound reaches it by `iter_postfixed` → `iter_persists`. The losing bound reaches it by `iter_shortens` → `iter_gives_persists` → `iter_persists (gives_mono …)`.

## 4. `kept_or_lost`: its successor case is one step with no `n`

In the successor case (ll. 107-130), `n` enters only through `L n d` (ll. 112, 120) and `KeptFor … n (seen a o)` (ll. 114, 119). It enters through the induction hypothesis in just one place, `(kept_or_lost n d)` at l. 123, applied to the code `d` that `updates` gives. Everything else does not depend on `n`: `inOrOut c`, `usableOrNot`, `everyValue`, `updates`, the two `each_or_some`, and `KeptFor.mono`. So the case is the following one-step statement, with `Φ := readingStep P sense guard allowed decode` (Keeping l. 355) and `Ψ := lostReadingStep …`:

```lean
theorem reading_or_lost_step (everyMove) (everyValue) (updates) (inOrOut) (usableOrNot) :
    ∀ (X Y : C → Prop), (∀ d, X d ∨ Y d) → ∀ c, Φ X c ∨ Ψ Y c
```

Its proof is ll. 107-130 with `kept_or_lost n d` replaced by `split d`. At each value, `X d` gives `⟨d, X d, fun s => (names s).mpr⟩ : coveredBy decode X (seen a o)`, and `Y d` gives `⟨d, names, Y d⟩`. The good side becomes `Usable ∧ ∀ o, coveredBy decode X (seen a o)`, and the final `.inl ⟨safe, a, usable, next⟩` is `Φ X c` by definition. The zero case `inOrOut` is the either-or of the two starts, because `iter Φ codeGuard 0 = codeGuard` and `iter Ψ Outside 0 = Outside`.

The general theorem is not found in what was read (`PredicateIteration` whole has no statement about two iterates). It needs no monotonicity:

```lean
theorem iter_either {Φ Ψ : (T → Prop) → T → Prop} {V₀ W₀ : T → Prop}
    (zero : ∀ t, V₀ t ∨ W₀ t) (step : ∀ X Y, (∀ t, X t ∨ Y t) → ∀ t, Φ X t ∨ Ψ Y t) :
    ∀ n t, iter Φ V₀ n t ∨ iter Ψ W₀ n t
  | 0 => zero
  | n + 1 => step _ _ (iter_either zero step n)
```

Then, by hand:

```lean
kept_or_lost n c = (iter_either inOrOut (reading_or_lost_step …) n c).imp (iter_iff_kept updates n c).mp id
```

**The bridge is `Viability.iter_iff_kept` (Keeping l. 369), `.mp`.** It turns `iter Φ (codeGuard decode guard) n c` into `KeptFor … n (decode c)`. `KeptFor` is defined by recursion on classes `S → Prop` (Keeping ll. 95-99), and `Lost` is an iterate on codes. `iter_iff_kept` is what puts the kept side on codes. Its cost is the premise `updates : ∀ c, (∀ s, decode c s → guard s) → ∀ a, Usable … (decode c) a → ∀ o, ∃ d, ∀ s, decode d s ↔ Seen … s`. That is the module's `updates` with `Names` and `codeGuard` unfolded (both are a `def`/`abbrev` of exactly that form), so the bridge adds no premise to `kept_or_lost`, which already has it. The `.mp` direction needs no `updates` mathematically: its half of the proof, Keeping ll. 371-372, is `KeptFor.mono sub hd` alone. But `iter_iff_kept` as stated takes `updates` for both directions together.

The content of `kept_or_lost` is therefore `reading_or_lost_step`: the two `each_or_some` and the decisions. Its induction on `n` is generic.

## 5. `lost_not_kept`: could it be a general never-both?

It is GuardHorizon `lost_not_viable` written again (§1). A general never-both in the iterate form

```lean
theorem iter_never_both (zero : ∀ t, V₀ t → W₀ t → False)
    (step : ∀ X Y, (∀ t, X t → Y t → False) → ∀ t, Φ X t → Ψ Y t → False) :
    ∀ n t, iter Φ V₀ n t → iter Ψ W₀ n t → False
```

**does not apply with `Φ = readingStep` as defined.** Its `step` premise is false there. `readingStep X c` gives, at each value, a covering code `e` with `X e` and `Seen ⊆ decode e`. The reply in `Ψ Y c` gives a possibly different code `d` with `Names d Seen` and `Y d`. If `X` and `Y` are disjoint and `d ≠ e` name the same class, both can hold. It would need `X` closed under narrower codes, which is true of `iter Φ codeGuard n` only through `iter_iff_kept` + `KeptFor.mono`, and so costs `updates`. `lost_not_kept` as stated has no `updates`.

Without that cost, the never-both is stated over a family below a step:

```lean
theorem below_never_both {stage : Nat → T → Prop}
    (zero : ∀ t, stage 0 t → W₀ t → False)
    (below : ∀ n t, stage (n + 1) t → Φ' (stage n) t)
    (step : ∀ X Y, (∀ t, X t → Y t → False) → ∀ t, Φ' X t → Ψ Y t → False) :
    ∀ n t, stage n t → iter Ψ W₀ n t → False
```

To get `lost_not_kept`, take `stage n d := KeptFor … n (decode d)` and `Φ' X c := codeGuard decode guard c ∧ ∃ a, Usable … (decode c) a ∧ ∀ o d, Names decode d (Seen … (decode c) a o) → X d`. Then `below` is `KeptFor.mono (fun s => (names s).mp)`, as at l. 80, with no `updates`. `step` is the three-way contradiction of ll. 77-79. `zero` is l. 76. Not found in what was read.

## 6. GuardHorizon's loss section: written again, and one statement for both

The scratch module writes GuardHorizon's loss section again with codes in place of configurations:

| GuardHorizon (configurations) | ScratchTwoSides (codes) | How |
|---|---|---|
| `lostStep` (l. 294): `¬ guard s ∨ ∀ a, ¬ Enabled P s a ∨ ∃ t, P.step s a t ∧ X t` | `lostReadingStep` (l. 28): `Outside decode guard c ∨ ∀ a, ¬ Usable P allowed (decode c) a ∨ ∃ o d, Names decode d (Seen …) ∧ X d` | Same shape. |
| `lost_mono` (l. 298) | `lostReading_mono` | Term repeated. |
| `lost_start` (l. 302) | `lostReading_start` | `Or.inl` both. |
| `lost_commutes` (l. 326) | `lostReading_commutes` | Term repeated. |
| `lost_shortens` (l. 336) | `lostReading_shortens` | Same call. |
| `lost_not_viable` (l. 318) | `lost_not_kept` | Induction repeated. |

**It cannot be a call of GuardHorizon as the definitions stand.**

- Over a process on codes `Pc.step c a d := ∃ o, Names decode d (Seen … a o)`, the start of `lostStep` is `¬ guardC`. With `guardC := codeGuard`, that is `¬ codeGuard c`, which is constructively weaker than `Outside c`. They agree only given `inOrOut`.
- `¬ Enabled Pc c a` is not `¬ Usable … (decode c) a`. A usable move with no code for some seen class is "not enabled" on codes.
- GuardHorizon's `lost_not_viable` is stated at `{S A : Type}`, universe 0, and the scratch module's `C`, `A` are in arbitrary universes.

**ONE statement could give both.** Generalise the step to `lossStep (bad : T → Prop) (dead : T → A → Prop) (next : T → A → T → Prop) X t := bad t ∨ ∀ a, dead t a ∨ ∃ u, next t a u ∧ X u`, and prove `mono`, `start` (`Or.inl`), `commutes` (by `gather_listed`), `shortens` and `within_length` once, plus `below_never_both` (§5) for the refutation.

- `lostStep P guard` is definitionally `lossStep (¬ guard ·) (fun s a => ¬ Enabled P s a) P.step`.
- `lostReadingStep` is that with `bad := Outside decode guard`, `dead c a := ¬ Usable … (decode c) a`, `next c a d := ∃ o, Names decode d (Seen … (decode c) a o)`. This holds up to the order `∃ o d, Names ∧ X d` against `∃ d, (∃ o, Names) ∧ X d`, which is not definitional. Redefining `lostReadingStep` in the second order makes it definitional.
- `lost_not_viable` is `below_never_both` with `stage := Viable P guard`. Its `below` is the definition of `Viable (n+1)`.

Then `lostReading_mono/start/commutes/shortens/within_length` and `lost_not_kept`, and GuardHorizon's `lost_mono/start/commutes/shortens/not_viable`, would all be calls. Not found in the package in what was read.
