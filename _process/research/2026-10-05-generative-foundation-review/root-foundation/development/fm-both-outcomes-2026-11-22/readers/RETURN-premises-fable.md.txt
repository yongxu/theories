**`inOrOut` is the conclusion at horizon 0.** `KeptFor P sense guard allowed 0 B` is `∀ s, B s → guard s` (`Keeping.lean` l. 97), which is `codeGuard decode guard c` at `B := decode c` (`abbrev`, l. 343). `Lost … 0 c` is `iter … (Outside decode guard) 0 c`, which is `Outside decode guard c` (`PredicateIteration.lean` l. 78). So

```lean
(inOrOut : ∀ c, codeGuard decode guard c ∨ Outside decode guard c)
```

is `∀ c, KeptFor P sense guard allowed 0 (decode c) ∨ L 0 c`, and l. 106 could not typecheck otherwise:

```lean
theorem kept_or_lost : ∀ n c, KeptFor P sense guard allowed n (decode c) ∨ L n c
  | 0, c => inOrOut c
```

The brief's T3 names "a premise that hands in the outcome (for example that `KeptFor` or `Lost` is decided)". This premise decides `KeptFor 0` against `Lost 0` for every code. It hands in the outcome at 0 and nothing above 0. Since it is an instance of the conclusion, no theorem of the form `∀ n c, KeptFor n … ∨ L n c` can do without it. What the theorem proves is that the either-or at 0 goes up to every horizon; it does not prove the either-or at 0.

It is not a classical principle as a premise: for a listed type of codes it is finitely many decisions, each supplied by the user. Its form is stronger than `p ∨ ¬ p`: the right side is a witness (`∃ s, decode c s ∧ ¬ guard s`), the left a `∀`. For a class given by an arbitrary predicate on an unlisted `S`, that is a decision of the kind "all, or a counterexample", per code.

## 2. `inOrOut` and `usableOrNot`: is a weaker decision enough?

**`inOrOut`.** For `kept_or_lost` as stated, with `Lost` started from a witness: no, because the premise is its instance at 0. Three ways to ask less, each changing something else:

- **Fewer codes.** The recursion calls `inOrOut` at `c` and at the codes `updates` gives (l. 107, then l. 123 `kept_or_lost n d`). A predicate on codes closed under those successors, with `inOrOut` asked only inside it, would do for the codes inside it. The statement would then carry that predicate.
- **A negation in place of the witness.** Start `Lost` from `fun c => ¬ codeGuard decode guard c` (as `GuardHorizon.lostStep` starts from `¬ guard s`, `GuardHorizon.lean` l. 294). Then the premise is `codeGuard decode guard c ∨ ¬ codeGuard decode guard c`, one proposition decided per code, which `Outside` implies and which does not imply `Outside`. Reading the proofs: `lostReading_start` stays `Or.inl`; `lostReading_commutes` passes the left disjunct through unchanged (l. 54); `lost_not_kept` at 0 becomes `outside kept`; `kept_or_lost` is unchanged in shape. The price is on the losing side: a lost code would no longer give a configuration outside the guard, so the loss is not "said positively" as the brief's Part A asks. A trade, not a gain.
- **From more primitive data.** Where each class is a listed set of configurations and the guard is decided at each configuration, `inOrOut` follows by `Undecided.each_or_some`. That is how the case proves it (`none_in_or_out`, ll. 165 to 173, by cases on levels). More is listed, less is decided at once.

**`usableOrNot`.** Used at l. 115 and nowhere else:

```lean
      have sides (a : A) : bad a ∨ good a := match usableOrNot c safe a with
```

So: at a guarded code, at a successor horizon, for each move. Not at horizon 0, not at a code with a configuration outside, not in Part A (the loss step carries `¬ Usable` as a disjunct, so `lostReading_commutes` needs no decision), not in Part B, not in the second half of `closed_or_lost_within`. The report says this (REPORT ll. 74, 77, 97) and it is right. It cannot be dropped: with one move and a guarded code all of whose seen classes are guarded, the conclusion at horizon 1 is `Usable … a ∨ (¬ Usable … a ∨ ∃ o d, … ∧ Outside … d)` with the last disjunct impossible, which is the decision itself. It is asked a little more often than the argument strictly needs (where some value already leads to a lost code, usability need not be known), but I found no plain way to state that narrower premise without the horizon in it.

## 5. What the statement is, and is not

**What it is.** There is a process (which configurations a move can lead to from a configuration), a guard on configurations, a condition on moves, and a reading that gives a value for each step. A class of configurations is what the chooser cannot tell apart. A move can be taken from a class only if it is allowed and enabled at every configuration of it; after it, the value the step gave narrows the class to what could stand now. A type of codes names some classes, and the codes must be closed under this: after a usable move from a code whose class is within the guard, at every value, some code names exactly the class seen. To have the either-or, three things must be on lists (every code, every move, every value) and two things must be decided (of each code: within the guard throughout, or a configuration of it outside; of each such code and each move: usable or not). Not asked: that the configurations be listed or finite, that a step or the guard be decided at a configuration, any equality test. Then of each code exactly one holds. Either its class lies in a family of classes within the guard, each with a usable move that leads, whatever value comes, back into the family (so the class is kept for every number of steps). Or it is lost at the level of the code list's length: whatever move is taken, some value leads to a class lost one level sooner, down to a class with a configuration outside the guard, or to a class from which no move is usable. The only numbers in the law are the horizon and the length of the list. The level of the Drain case is in the case only: there a configuration is a lane and a level, the guard is "the level is not zero", and a move that does not match the lane lowers it. The law has a guard and no quantity.

**What it does not say.** Nothing is drawn down in the law: no stock, no amount, no rate, no share, nothing that locks. There is no time of reading: the reading gives a value at every step, and no statement compares reading sooner with reading later, or "early enough". It does not compare two readings; that one process is kept under one reading and lost under another is shown by the built case alone, and the either-or itself was applied only to the reading that keeps nothing (the level reading's values are all the numbers and cannot be listed as the premise stands). "Lost" does not mean that a course leaves the guard: a class with no usable move is lost at level 1 though nothing moves, and no theorem in the module turns `Lost n c` into a run of the process that reaches a configuration outside the guard (not found in what was read: the module whole). The bound is the length of a list, not the least level: 9 against 3 in the case. It has one chooser against every outcome; nothing of many who choose, of a selection, of what sustains it. It says nothing of how the two ways stand to each other.

**Its name in the literature.** This is the known result that a safety game with partial observation is decided on the game of knowledge sets: the classes are the knowledge (belief) sets, `updates` is the subset construction closed under the observation update, the kept side is the largest set of knowledge sets closed under a controllable step (in control: a controlled invariant set, or viability kernel, under partial observation), the losing side is the least fixed point of the opponent's step, and the either-or with a bound of the number of positions is the determinacy of a finite safety game by backward induction. Sources I am confident of: Reif, "The complexity of two-player games of incomplete information" (1984); De Wulf, Doyen and Raskin, "A lattice theory for solving games of imperfect information" (2006); Chatterjee, Doyen, Henzinger and Raskin, "Algorithms for omega-regular games with imperfect information" (2006/2007). In planning the reading that keeps nothing is conformant planning and a reading with values is contingent planning in belief space. What differs here: (a) nothing classical: the listings and the two decisions are stated premises, and the losing side's bound is also proved with nothing decided (Part A.2, by commuting with implication over a listed set of moves); (b) the knowledge sets are an abstract type of codes with `decode`, the configurations need not be listed; (c) the value read is of the step, not of the configuration reached, and a move must be usable at every configuration of the class; (d) the literature's theorem ties the knowledge game to strategies that depend only on observations in the original game; here that tie exists on the kept side only (`keptFor_iff_plan`, for values in `Fin k`), and the losing side is tied to plans only as a negation (`lost_not_kept`). As mathematics it is not new; its use here is as a join of the package's two sides.

## 6. Empty cases

- **An empty class** (a code `c` with `decode c` true of nothing). `codeGuard` holds vacuously, `Outside` fails, every move is usable vacuously. With a move in the type: kept at every horizon (`keptFor_empty`), in a closed family, never lost. With no move: see the next item. The statements are true and not vacuous. Note what "kept" then says: a class of nothing is kept for ever, and `updates` forces such a code to exist wherever some value is given by no step (the code `.empty` in the level reading).
- **An empty type of moves.** `moves := []`. `KeptFor (n + 1)` fails for every class (it asks a move); `L (n + 1) c` holds for every code, since `∀ a, …` over no moves is vacuous (l. 30). `kept_or_lost`: at 0 it is `inOrOut`; above 0 the right side. `closed_or_lost_within`: no class is in a closed family (the family asks a move); `L all.length c` holds because a code exists, so `all.length ≥ 1`. True, not vacuous, and degenerate: every code is lost at 1, a guarded one too, though nothing ever leaves the guard. `everyValue`, `updates` and `usableOrNot` are vacuous here.
- **An empty type of values** (not asked; for completeness). `values := []`; `updates` is vacuous; a class is kept for ever exactly where it is within the guard and has a usable move, and lost at 1 otherwise. True, not vacuous.
- **An empty type of codes.** `all := []`. Every theorem that takes a code is vacuous: `lostReading_start`, `lostReading_shortens`, `lostReading_within_length`, `lost_not_kept`, `closed_never_lost`, `kept_or_lost`, `closed_or_lost_within`. `lostReading_mono` and `lostReading_commutes` hold trivially of predicates on an empty type.
- **A code list with repeats, or two codes naming one class.** Allowed: `every` asks membership only. The statements stay true and say something; the bound is the list's length, not the number of distinct codes or classes, so a longer list gives a weaker bound on the losing side and asks more on the kept side. The docstring's "code-list length" is exact about this. Listing the codes outside the guard also lengthens the bound for no gain (section 4).
