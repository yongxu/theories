## 0. The file's step, as opened

OPENED, `PopulationCorrection.lean` ll. 9–48:

```
15 def funded (fee : Nat) (s : State) : Bool := decide (fee ≤ s.reserve)
33 def allocated (N k : Nat) (active : Bool) (r : Nat) : Nat :=
34   if active then min N (r + k) else r - k
36 def inflow (N : Nat) (active : Bool) (r : Nat) : Nat :=
37   r + if active then 3 * (N - r) else 0
39 def next (N fee cap k : Nat) (s : State) : State :=
40   let active := funded fee s
41   { renewing := allocated N k active s.renewing
42     reserve := min fee (s.reserve - (if active then fee else 0) +
43       inflow N active s.renewing)
44     capacity := min cap (s.capacity + s.renewing - (N - s.renewing)) }
```

Six things follow from this.
- **The schedule.** `k t` is the number of slots that revise at step `t` (`history`, l. 48).
- **The rule.** `funded` is not stored. It is recomputed at every step from the reserve.
- **The reserve rises while correction is unfunded.** Unfunded (l. 52): `⟨s.renewing-k, min fee (s.reserve+s.renewing), …⟩`. Each renewing slot pays one into the reserve. So under no correction the reserve rises by the number renewing, while that number falls by `k`.
- **Funded stays funded.** Funded (l. 60), under `hr : s.renewing ≤ N`, `hf : fee ≤ N` and `hb : fee ≤ s.reserve`, the reserve becomes exactly `fee`. This is `correction_stays_funded`, l. 94.
- **Nothing reads capacity.** Capacity appears only on the right of its own update (l. 44). No other field and no `funded` reads it.
- **No need, and a total step.** Nothing in the file cuts the course when a level falls below anything.

The boundary is `exact_schedule_activation_boundary` (OPENED, ll. 504–507):

```
(hr : s.renewing ≤ N) (hf : fee ≤ N) (hk : ∀ t, 1 ≤ k t) :
(∃ t, fee ≤ (history N fee cap k s t).reserve) ↔ fee ≤ s.reserve+available k s.renewing s.renewing
```

Here `available k r r` is the sum of the counterfactual renewing counts `offCount k r 0 … offCount k r (r-1)` (ll. 381–387). The proof uses three things:
- `funding_iff_ledger` (l. 496): at each `t`, funded iff `fee ≤ s.reserve + available k s.renewing t`. It rests on `actual_or_unfunded_ledger`, l. 464, which says the unfunded reserve is exactly `s.reserve + available … t`.
- `contributions_bounded` (l. 456): `available k r t ≤ available k r r`.
- `contributions_stop` (l. 446): contributions stop after `r` steps, because `off_count_bound` (l. 407) gives `offCount k r t ≤ r - t`.

**One statement with both outcomes?** OPENED. There is no single statement. `exact_schedule_activation_boundary` is one iff about reaching funding. The two regions are two further theorems under the same condition and its negation, side by side:
- `schedule_shortfall_is_destructive`, l. 524, with premise `shortfall : … < fee`;
- `schedule_sufficiency_is_constructive`, l. 553, with premise `enough : fee ≤ …`.

### Q3.2 Each package law, premise by premise

**(a) `locked_turns_in_time_share_iff` (l. 1876).** OPENED.

*What it states.* Take a `Locked` way `w` at level `x < H₁ + y₁`, with `x ≤ hi`. The net `net need (windowAfterShare …) (fun w x => RegimeMargin.step giving (use w) x)` never ends from `(w, x)` exactly where there is a step `T` of the course as it was with all of:
- the need met at every `j < T`, with no level in `[N, K)` before `T`;
- the need met at `T`, and the level at `T` in `[N, K)`;
- `H₂ + y₂ ≤` the level at `T + 1`.

*Premises, and what in the file would discharge each:*
- `raises : Raises P favours fA` (`∀ x g, favours g → P.le x (f x g)`, RuleCapture l. 145). Take the share to be `r` alone, ordered by `≥`, and the favoured rule to be unfunded. Then `allocated N k false r = r - k ≤ r` discharges it. But the share cannot then carry the reserve. If the share is `(r, B)`, the unfunded step sends `B` to `min fee (B + r)`, which is below `B` wherever `B > fee` (l. 42). Then `Raises`, which quantifies over every share, fails for any order in which a higher reserve counts as a higher share. Restricting to a subtype `B ≤ fee` was not tried.
- `monotone : ReadsShare P M hA` (`∀ x y g g', P.le x y → M.le (h x g) (h y g')`, l. 150). **Nothing discharges it.** The file's rule is read off the reserve (l. 15), and the reserve is accumulated history. There are three ways to place the reserve, and each fails:
  - In the share: under the unfunded rule the reserve rises (l. 52), and a higher reserve reads the rule toward funded. The reading then moves against the favoured rule, which is the opposite of what `ReadsShare` with `upper` keeps.
  - In the rule `R`: `ReadsShare` asks the reading to be monotone "whatever rules the two readings meet", so it cannot depend on a reserve carried in the old rule.
  - Ordered away (an order on `r` only): two shares equal in `r` and different in `B` read different rules. That forces `M` to equate `true` and `false`, and then `upper` fails.

  This is argued from the definitions. I did not try every preorder, and a reader could dispute it by giving an encoding of the reserve that I did not think of.
- `upper`. Holds trivially for any `M` with `false` and `true` incomparable. Not needed once `monotone` has failed.
- `sets`, `lowRule`, `lowStays` (window sets a `Low` share and a `kept` rule; the rule read off a `Low` share is `kept`; a `kept` rule keeps a `Low` share `Low`).
  - Nearest in the file: once funded, the reserve stays at `fee` (`funded_step` l. 57, under `hr`, `hf`, `hb`), and `renewing` rises to `N` (`funded_replacement_bound` l. 161).
  - With `Low := fee ≤ B`, `lowStays` is the shape of `funded_step`'s reserve conjunct. It is discharged by the supplied charges (`1` and `3`, l. 37) with `hf : fee ≤ N`: `fee ≤ s.reserve - fee + s.renewing + 3*(N - s.renewing)` (l. 62).
  - `sets` has no counterpart. Funding does not *set* the share. It changes the direction in which `allocated` moves it.
- `uses` (kept kind uses `H₂`), `nothing`, `short`, `meets`, `keeps` (regime giving at `H₂`), `needs`, `within`, `short₁`, `draws`, `below`, `high`.
  - **Nothing in the file discharges `uses`, `meets`, `needs` or `within`.** The level that the window reads would be the reserve, and its funded update `min fee (B - fee + r + 3(N-r))` depends on the way, so it is not a regime step.
  - On capacity instead: `nothing` and `keeps` hold for giving `0`. `short` holds trivially for any `y` when `H > 0`. `meets` fails for `H > 0` on any band where `y + H ≤ hi`. `needs` has nothing.

*Verdict.* Not the same law in other names, and not a case. The same shape with roles turned (§Q3.3).

**(b) `locked_ends_rising` (l. 1499).** OPENED.

*What it states:* "`∃ n t, n ≤ hi + 1 ∧ «迭» (net need after (fun w x => RegimeMargin.step giving (use w) x)) n (w, x) t ∧ (∀ v, ¬ net … t v) ∧ t.1 = Law.orbit (windowAlone fA hA reads) w n ∧ Locked …`".

*The best pairing:* level := capacity, `need := 1` (supplied by me, not the file), giving `0`, use `N - 2r`, no marks (`marked := fun _ => False`, so `outside` and `un` hold, since the way's step never reads capacity).
- `nothing`, `keeps` (`Keeps 0 0 hi`: the step `x ↦ x` stays within `hi`) and `high` (`v ≤ cap =: hi`) are discharged.
- `raises`, `monotone`, `upper` and `locked` are not (as in (a)).
- `more` (`∀ v …, use v < use (windowAlone fA hA reads v)`) fails at `r = 0`. There `r - k = 0`, so the use stays at `N` and does not rise. `more` is asked at every way not below the start, and the `r = 0` ways are among them.

Even where it applies, the regime form holds only on ways with `2r ≤ N`. So the pair's step (defined at every way) would agree with the file's only along the part of the orbit where `2r ≤ N`. That agreement is a lemma not stated anywhere I read.

The file proves its ending by its own arithmetic: `destructive_region_reached` l. 282, witness `t := s.renewing + z.capacity` (l. 298), through `extinct_unfunded_history` l. 264.

*Verdict.* Same shape (a course that ends within a bound), not a case.

**(c) `recoverable_iff_above` (l. 2146).** OPENED.

*What it states:* "`Recoverable (Turned X giving H) (MeetsNeed need) (fun t _ => X t) N ↔ H + y ≤ X N`". The premises are:
- `fall : ∀ t, X (t + 1) ≤ X t` and `top : X 0 ≤ hi`;
- `nothing`, `short`, `meets`, `keeps` at `H`, `y`, `hi`;
- `needs`, `within`.

The feasible courses are `X` turned to the standing use `H` at some step (`turned`, l. 1999).

*In the file, the quantity that decides does not fall.* Along the unfunded course, `actual_or_unfunded_ledger` (l. 464, right disjunct) gives `reserve_t = s.reserve + available k s.renewing t`. So the reserve plus what the renewing can still pay is the same at every step before funding, `s.reserve + available k r r`. That potential is the only candidate for `X`, and it is constant (argued). `fall` holds trivially, but:
- No family of feasible courses in the file plays the part of `Turned`. The file's only alternatives are `topup` (l. 246), `leakingNext` (l. 641) and `drainedNext` (l. 664).
- `RegimeMargin`'s premises (`meets`, `needs`, `within`) have nothing to discharge them.

*What the file's own statement gives instead.* Its own statement shows that the outcome has no point of no return in time.

At the absorbing state `⟨0, B, 0⟩` with `B < fee` (`destructive_region_absorbing` l. 594), `exact_schedule_topup` (OPENED, ll. 516–519) gives `(∃ t, fee ≤ (history … (topup fee extra s) t).reserve) ↔ fee-(s.reserve+available k s.renewing s.renewing) ≤ extra`. With `s.renewing = 0` this reads `fee - B ≤ extra`, because `available k 0 0 = 0` by l. 386. `schedule_sufficiency_is_constructive` (l. 553) then takes that start to all renewing with capacity at `cap`.

So the "for good" of the destructive region is absorbing under the file's step alone. A top-up of `fee - B` leaves it at whatever step it comes, and lost capacity comes back. Before `r` reaches 0 the needed top-up is the same constant `fee - (s.reserve + available k r r)` at every step (argued from the ledger and `history_add` l. 257; I did not check the shift of `offCount` in Lean).

In the package's law the turn is possible only while a falling level is at or above `H + y`. In the file nothing that decides falls, and what falls (capacity) is read by nothing.

*Verdict.* Not a case. The role is turned in time: the package's window to turn closes, and the file's does not.

Argued, not Lean.

### Q3.3 What exactly is turned, and whether a turned law is stated

OPENED on both sides.

**1. Feedback on the reading.**
- *Lock:* `Raises` with `ReadsShare` and `upper` (`turn_locked`, RuleCapture l. 169). Under the favoured rule the share rises, and the rule read off a higher share stays favouring. The feedback on the rule is positive.
- *File, unfunded:* the favoured (racing) count rises under `allocated` (supplied). But the rule is read off the reserve, which the *unfavoured* (renewing) fill at one each (l. 37). Under the favoured rule the reading moves *toward* turning, and the feedback on the rule is negative. Whether the turn comes depends on whether the favoured rule drains the unfavoured before they have paid `fee`. That is the ledger `s.reserve + available k r r` against `fee`.
- *Where a lock appears in the file:* only at the end (`r = 0`), where the inflow stops (`min fee (B + 0) = B`) and `⟨0,B,0⟩` is a fixed point (l. 594). It is a fixed point, not a moving lock.

**2. Which side holds itself.**
- *Lock:* the favouring rule's region is closed (`locked_closed` l. 1291) while the unread level falls.
- *File:* the *correcting* rule's region is closed (`correction_stays_funded` l. 94), and under it the unread level rises to `cap` and stands. `schedule_sufficiency_reaches_full_state` l. 576: `history … (t+u) = ⟨N,fee,cap⟩` for all `u`.

The constructive outcome is a fixed state, i.e. a standstill. Note `locked_closed` allows any `fB`, so a closed region with an unread level that rises is covered *in shape* by `locked_closed`. It is not covered as a case, because the file's funded rule is not read off a share (Q3.2(a)).

**3. What triggers the turn.**
- *Lock (window):* a falling level enters `[N, K)`, and the turn in time needs the level still at or above `H₂ + y₂` one step later.
- *File:* a rising level (the reserve) reaches `fee`, a reachability `∃ t`. Once reached it stays (l. 94), so `∃ t` is "from some step on, always".

**4. Who pays whom.**
- *Lock:* the favoured are raised by the selection (`Raises`), and the level under the lock pays the use `H₁` (`draws`).
- *File:* the renewing pay `1` each into the reserve at every step. Once funded, the reserve pays `fee` and the racing are charged `3` each (l. 37). The renewing are not paid by anything modelled; their payoff is `payoff`, l. 17, which no field reads.

**Is a turned law stated in the package?** The nearest is `ClosedCapture.turned_by_loss` (OPENED, ll. 291–295). It states: where `turns : ∀ p g, N ≤ p.2 → ¬ favours (h p g)` and `accrues : Accrues fB` (`∀ p g, p.2 + 1 ≤ fB p g`, l. 273), the rule in force at `r + 1`, after a reading step `r` with `N ≤ b + r`, does not favour.

The map: the accumulator `p.2` := reserve, `N` := `fee`, and `h` reads the accumulator. This is an accumulating quantity crossing a bound and turning the rule, the file's mechanism.

`Accrues` fails in the file exactly where its content lies. `min fee (B + r) = B` at `r = 0`, and the inflow is bounded by `available k r r`, which the unfavoured rule itself shrinks (`faster_replacement_reduces_available` l. 398). There is also a one-step lag: `Pace.turn` reads the old configuration (`Pace` l. 102), while the file's `funded` acts at the step it reads.

So the package has the turn by an accumulation that never stops. A turned law in which the accumulation is bounded by what the drained side can still pay, with the exact ledger boundary, was not found in what was read.

## Q9. A case with the statement unchanged, or beside?

**Law of a list: `iter_iff_all` (l. 153), `iter_within_length` (l. 255).** OPENED.

*What `iter_iff_all` states:* "under `mono : MonotoneStep Φ`, `start : ∀ y, Φ V₀ y → V₀ y` and `within : ∀ x, V₀ x → x ∈ all`: `iter Φ V₀ all.length y ↔ ∀ n, iter Φ V₀ n y`".

*The file's boundary has a similar form.* `exact_schedule_activation_boundary`'s proof turns `∃ t` into "at `t = s.renewing`" (l. 514: `⟨s.renewing, …⟩`). That is an unbounded quantifier over steps reduced to one step at a count.

*The mechanisms differ.*
- The file's bound is the falling count `r`: contributions stop at `r` (`contributions_stop` l. 446, by `off_count_bound` l. 407).
- `iter_iff_all`'s bound is the length of a list that covers the start, which is a pigeonhole on listed states.
- `within` fails for the file's states as typed (`State` is three `Nat`s) and, more decisively, for a time-varying schedule. `history` depends on `k t`, so a configuration of the course must carry `t`, and `V₀` is then infinite.
- With a constant `k`, and states bounded after the first step (`count_bound` l. 68; `post_step_bounds` l. 570: `reserve ≤ fee`, `capacity ≤ cap`), a list of the `(N+1)(fee+1)(cap+1)` bounded states would exist. Then `iter_iff_all` with `Φ X s := ¬ funded fee s ∧ X (next … s)` would give "never funded iff unfunded for that many steps". That bound is far weaker than `r`, and it says nothing of the right side `fee ≤ s.reserve + available k r r`. Argued, not Lean.
- `iter_within_length` adds `CommutesWithImplication`, which has nothing in the file to meet it.

*Verdict.* It stands beside the law of a list and is not a case with the statement unchanged.

**`RegimeMargin`'s point of no return.** OPENED.

`ends_iff_below` (l. 741) states: "`(∃ n, (Law.run (step g H) x).state n = 0) ↔ x < H + y`", for one level under a standing draw `H` and a giving `g` read off the level, under `pos`, `short`, `nothing`, `meets`, `keeps`, `high`.
- The file's decisive pair (reserve rising by `r`, `r` falling by `k t`) is two quantities with a time-varying draw. That is not one `Law.run (step g H)`.
- On the falling count alone, at a constant schedule `k t = c`, the unfunded `renewing` is `RegimeMargin.step (fun _ => 0) c r = r - c`. So `offCount (fun _ => c) r t` equals `(Law.run (step (fun _ => 0) c) r).state t` (argued by unfolding l. 383 and l. 249, not checked). `ends_beyond_giving` (l. 721) then gives "gone within `r` steps".

  This is a dictionary for one piece (the file's `off_count_bound` at constant `k`), and with giving `0` the point of no return `H + y` is vacuous: every positive level ends.

`falls_or_bound` (l. 890) states: "`(∃ k, k ≤ n ∧ state k < b) ∨ (state n + (H - Y) * n ≤ x ∧ b ≤ state n)`" under `AtMost g Y`, `Y ≤ H`, `H ≤ b`. The file's `funded_or_replacement_bound` (l. 205) is "`fee ≤ reserve_t ∨ renewing_t ≤ s.renewing - t`".
- Both say "crossed a threshold, or a linear bound holds".
- In `falls_or_bound` the level that crosses and the level that is bounded are one level. In the file they are two (the reserve crosses, the count is bounded), and the crossing is upward.
- Under a map `b := fee`, `H - Y := 1`, they agree only in shape, not word for word.

*Verdict.* `RegimeMargin` matches in shape, and as a dictionary only for the count at a constant schedule. The file's boundary is not a case of `RegimeMargin`'s point of no return with its statement unchanged.

## Which of N1 to N5 holds

- **The lock (`TurningInTime` §6 and §7, `RuleCapture.Locked`):** N4. No package statement has the file's boundary as a case, because `ReadsShare` cannot hold of a rule read off an accumulator that the unfavoured fill, and the regime premises have nothing to discharge them. A join would need a lock law whose rule is read off an accumulated level fed by the unfavoured, with accrual bounded by what they can still pay (`turned_by_loss` without `Accrues`), and a need. Neither side has that. N3 holds of the file as to what carries the look:
  - the share's motion is the supplied `allocated`;
